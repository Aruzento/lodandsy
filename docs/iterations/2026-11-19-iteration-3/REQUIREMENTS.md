# LODANDSY — итерация 3: документы, сущности, карта и инструменты

Редакция: 19.11.2026. Базовый опубликованный коммит на момент подготовки: `1835e3bad0ef99f4aa84cd4412143e285cfeece9`, ветка `codex/mvp-cards-map-tools`. Перед реализацией сверить фактический HEAD, git status и Linear. Это техническое задание на следующую последовательную итерацию, а не описание уже реализованного результата.

## 1. Цель и источники требований

По результатам ручной проверки владельца исправить десять замечаний:

1. Карточки должны открываться как визуально оформленные редактируемые документы, не как Markdown-код.
2. Карточка персонажа должна иметь отдельный блок портрета.
3. Убрать искусственные разделы Cards/Maps/Tools в дереве: все документы равноправны и могут быть вложены друг в друга.
4. Сетка должна быть видимой и удобной при работе с картой.
5. Отказаться от отдельного типа «Маркер», его роль выполняет токен.
6. Токены персонажей круглые.
7. Размер обычного токена связан с размером клетки; предусмотреть другие размеры.
8. Разделить токены на персонажей (круг, белая рамка) и предметы (оригинальное изображение, без рамки).
9. Таблицы получат столбцы и основу для дальнейшего развития в базы данных.
10. Кубики получат визуальный интерфейс, количество кубиков каждого вида, результаты и сохраняемые заготовки.

При расхождении с прежним MVP эти требования имеют приоритет как новый продуктовый запрос. Предлагаемые ниже детали модели и поведения — инженерные решения, а не утверждение, что владелец уже подтвердил каждый нюанс. Существенный новый публичный формат и разрушительные операции требуют согласования. Изучить AGENTS.md, docs/MVP.md, ADR-001–012, существующие тесты и задачи. Не повторять работу, уже удовлетворяющую новым критериям.

## 2. Общие инварианты

- Windows-first, offline; Python, PySide6/Qt Widgets, Qt ADS, libvips/pyvips и существующий тайловый renderer сохраняются. Не вводить второй GUI-стек, полноценный браузер, сервер, облако, движок плагинов или игровую систему без необходимости и согласования.
- Модульный монолит: Core владеет общей идентичностью и иерархией, каждый модуль — своей предметной моделью и операциями. Qt и SQL не проникают в domain. Не переносить Map/Tools внутрь CardCollection, не делать универсальный контроллер всех игровых функций.
- Один канонический SQLite-проект (S3), исходные resources в assets, перестраиваемые caches отдельно. Не хранить вторую активную копию пользовательских данных, не делать параллельный формат сохранения. Один общий save pipeline с revision, dirty/saving/error, autosave и Ctrl+S. Транзакции, FK, блокировка второго писателя, валидация инвариантов, резервное копирование и понятные ошибки.
- Stable UUID сохраняются при миграциях и переносах; не переиспользовать ID. Ссылки и иерархия — разные отношения. Разорванные ссылки остаются диагностируемыми; обычный rename/reparent не меняет ссылок. Все модули используют единый asset adapter, проверяемые пути и bounded decode/cache.
- Qt ADS управляет размещением; WindowManager — lifecycle и уникальность открытого документа. Tree/Inspector фиксированы. Selection, active document и данные мира независимы. Один документ по kind/ID, выбор другого узла не переназначает открытое окно.
- Соблюдать офлайн-политику: никакой загрузки сетевых ресурсов, внешние http/https открываются только по явному действию в системном браузере; запрещать file://, javascript:, произвольные filesystem URLs, path traversal и выход через symlink/junction. Проверять ввод, HTML, ресурсы и clipboard. Не выполнять пользовательский код.
- Не менять работающий тайловый renderer ради оформления объектов. Сохранять производительность, UI thread не блокируется долгим IO/декодированием; не снимать защитные лимиты произвольно.
- Внешний вид: существующая navy/black + restrained gold тема, читаемая типографика, русскоязычные подписи, согласованные SVG-иконки, явные hover/selection/focus/disabled/error, корректные DPI. Интерфейс для человека, а не диагностический инструмент разработчика. Не добавлять кнопки-заглушки.

## 3. Блок A — единая иерархия сущностей (замечание 3)

Linear: ARU-34 (3.1), ARU-35 (3.2), ARU-36 (3.3, существующая реализация), ARU-37 (3.4), ARU-38 (3.5), ARU-39 (3.6). Связанные: ARU-69, ARU-28, ARU-65. Не создавать повторный проект или дубликаты задач.

### Текущее несоответствие

ADR-007 специально выбрал UI-группировку независимых данных. `ProjectTreeModel` наследует `CardTreeModel` и сохраняет отдельные разделы; DnD ограничен Cards. В schema 4 таблица `entity` фактически обслуживает Cards, Map/Table лежат отдельно, Dice является singleton-инструментом. Изменение требуется в канонических данных, не только в Qt-модели.

### Контракт и реализация

- Один минимальный Entity envelope: id, kind, title, parent_id (или null), position. Типизированный payload определяется модулем и имеет версию. Предпочтительно использовать существующую `entity` как структурный реестр всех документов, а модульные payload хранить отдельно по entity_id (согласованные FK). Избегать дублирования title/parent/order в payload. Не строить универсальную RPG Entity с десятками необязательных полей.
- Поддерживаемые документы: Card, Map, Table, DiceDocument. Любой из этих типов может находиться в корне и быть родителем/ребёнком любого другого типа. Внутренние объекты карты (TokenInstance, grid), строки/столбцы таблиц и единичные броски не являются самостоятельными узлами дерева в этой итерации. DiceDocument — именованный документ с сохраняемыми настройками; наборы бросков внутри него — часть payload. Можно оставить быстрый запуск кубиков, но не как обязательную псевдопапку дерева.
- Один Tree без фиксированных групп «Карточки», «Карты», «Таблицы», «Кубики». Иконка показывает тип. «+» создаёт любой поддерживаемый тип; контекстное меню позволяет создать дочернюю сущность любого типа. Открытие/фокус по ID, переименование, перемещение, reorder, удаление, поиск, контекстные действия и keyboard navigation работают одинаково. Существующие действия карточек и активные кнопки сохраняются; меню верхнего уровня не становится основным навигатором.
- Пример (не фиксированная структура):

  ```text
  Мир
  ├── Город (Card)
  │   ├── Карта города (Map)
  │   │   └── Подземелье (Map)
  │   │       ├── Информация о подземелье (Card)
  │   │       └── Случайные встречи (Table)
  │   └── Проверки охраны (DiceDocument)
  └── Персонаж (Card)
  ```

- Единое каноническое управление иерархией: запрет циклов в том числе между типами, отсутствующих родителей, duplicate IDs, неоднозначного порядка; согласованные create/reparent/reorder/delete. Удаление поддерева — с явным подтверждением количества/типов затрагиваемых документов и закрытием их окон. Не удалять размещённые на других картах токены при удалении их ссылочной цели. Inspector читает общий summary и данные поддерживаемого типа, не подменяет текущий документ.
- Миграция настоящего schema 4: сохранить Card-иерархию и позиции, существующие Map/Table UUID и их payload; прежние карты/таблицы без родителя добавить в корень в детерминированном порядке, не придумывать связи. Безопасно обработать старые layout keys (включая singleton `dice`); не создавать новые документы из старого UI state без осмысленной политики. Встроить базовый сохраняемый DiceDocument, не делать неработающий узел до блока F.

### Критерии готовности

Миграция реального старого проекта, создание и смешанный DnD минимум по одному документу каждого типа (включая встречный переход и запрет цикла), reorder, выбор/открытие, rename, поиск, сохранение/перезапуск, восстановление selection/expanded/layout, удаление смешанного поддерева, отказ ошибочной миграции с сохранением оригинала. Пройти зависимые Card/Map/Tools tests. Не отмечать ARU-36 повторно готовым без проверки расширенного контракта.

## 4. Блок B — визуальный редактор документов (замечание 1)

Linear: ARU-75 (6.6), связанные ARU-72, ARU-60, ARU-33.

### Новый UX

- Основной режим — редактируемый форматированный документ (WYSIWYG, «что видишь, то и получаешь»). Открытие существующей и создание новой Card показывают заголовки, списки, ссылки, изображения и оформление, а не `#`, `**`, `![...]` и HTML-теги. Не считать задачу выполненной простой сменой режима на read-only Preview. Редактирование, курсор, выделение и горячие клавиши работают непосредственно в красивом документе.
- Панель действий документа: заголовок/обычный абзац, шрифт, размер, цвет, жирный/курсив/подчёркивание/зачёркивание, выравнивание, списки, цитата, код, разделитель, ссылка на сущность, локальная картинка, Undo/Redo. Состояния кнопок соответствуют курсору/выделению; действия действуют только на активный редактор. Ограничить палитру и размеры разумными поддерживаемыми значениями. Rich formatting сохраняется как содержимое документа; масштаб просмотра не меняет содержимое. Удобный режим чтения допустим; Markdown/raw source — только дополнительный экспертный режим, если его можно поддерживать без потерь. Новым пользователям он не навязывается.
- Сохранить прежние `lodandsy://card/UUID` и относительные ссылки на assets. Вставка внутренних ссылок через выбор существующей сущности; если расширяется публичная схема на другие kind — обозначить в ADR. Ссылка открывает/фокусирует цель отдельно, broken link понятен и не исчезает сам. Внешние ссылки и локальные изображения подчиняются общей политике безопасности.

### Архитектура формата — обязательная точка решения

Предпочтительный кандидат для раннего прототипа: `QTextEdit` + защищённый `QTextDocument`, версионируемый контролируемый HTML subset для текстовой части (не полноценный браузер). Альтернатива — компактный структурированный JSON/типизированные блоки, если требования к структуре и round-trip объективно требуют этого. Сравнить исходный Markdown, ограниченный HTML и структурированную модель по визуальному редактированию, сериализации, поддержке шрифтов/цветов, изображениям, ссылкам, Undo, поиску, совместимости и стоимости разработки. Проверить на реальных старых документах, а не только на одном жирном слове. Qt rich text поддерживает подмножество HTML, `toMarkdown()` теряет часть форматирования (например шрифты/цвет); нельзя использовать его как бесконечный цикл rich text→Markdown→rich text.

- Разделить envelope Card, версионируемый DocumentContent и пользовательские настройки вида. HTML/XML допустимы как внутреннее представление, но не как разметка, которую должен вводить пользователь. Для структурированных блоков вроде портрета использовать явные поля/типизированные данные (блок C), а не извлекать произвольные теги регулярными выражениями.
- Сохранить одну каноническую редакцию конкретного документа. Для наследуемого Markdown до подтверждённого безопасного преобразования сохранять оригинальный текст как канонический legacy payload, не переписывать его при открытии/просмотре. После явной конвертации или согласованной миграции — новая версия payload, прежний исходник только как backup/архив миграции, не второй редактируемый источник. Когда возможна потеря нестандартной разметки, показать предупреждение и оставить старый вариант доступным; никакого тихого усечения. Не сбрасывать Undo при каждом обновлении/получении сигнала. Не вызывать setHtml/setMarkdown в цикле на каждое нажатие.
- Брать разрешённые структуры/атрибуты по whitelist; блокировать scripts, iframe, forms, remote CSS/fonts/images, произвольные URL, вредоносные вставки из clipboard. Проверить document-level resource loader и fallback: одного запрета внешних ссылок недостаточно. Проверить ссылки, код, вложенные списки, таблицы, Unicode, смешанный Markdown/HTML, missing assets, unsupported legacy content. Не считать Qt HTML сериализацию идентичной исходным байтам.
- ADR на публичный формат и миграцию обязателен. Если прототип подтверждает вариант — представить одно конкретное краткое решение владельцу до production-записей нового формата; не останавливать работу на каждой UI мелочи. Не выполнять массовую конвертацию реальных пользовательских миров в процессе разработки. После утверждения реализовать безопасную миграцию/конвертацию тестовых копий.

### Критерии готовности

С нуля открыть красивый редактируемый документ; на выделении применять и снимать оформление, вставлять локальные картинки/ссылки, отменять/повторять, редактировать разные документы одновременно, закрывать/открывать; сохранять и восстанавливать содержимое, композицию и форматирование после рестарта. Проверить legacy Markdown без потерь (в том числе непреобразуемую разметку), поиск по тексту, перенос проекта, backup/restore, смену темы и DPI. Добавить fixture corpus и semantic round-trip tests (не только сравнение HTML-строк). Предоставить кадр реального Windows UI и короткий сценарий ручной проверки владельцу.

## 5. Блок C — портрет персонажа и шаблоны (замечание 2)

Linear: ARU-76 (6.7), после ARU-75.

- Шаблоны Card остаются универсальными документами: пустая карточка, статья, персонаж, локация, предмет. Создание даёт независимую копию начального содержимого; новые шаблоны создают оформленный документ без видимых Markdown-символов.
- В шаблоне «Персонаж» отдельный чёткий портретный блок: рядом с заголовком/основными сведениями или над текстом при узком окне. Не навязывать изображение; пустое состояние «Добавить портрет». Выбор, замена, удаление, при необходимости увеличение по щелчку; сохранять пропорции, без неконтролируемой загрузки исходного размера. Подпись необязательна. Обычные inline-изображения в тексте остаются независимыми.
- Стабильная ссылка на `asset_id` в versioned Card payload или типизированном PortraitBlock, необязательное alt/caption. Общий asset adapter, не base64 в rich text, не абсолютный путь. Привязка портрета сохраняется в проекте, не в локальном UI state. При удалении портрета не уничтожать общий asset, на который ещё есть ссылки, включая карты и токены. При отсутствующем ресурсе — заглушка и возможность замены.
- Не вводить персонажа как отдельный RPG kind и не реализовывать расчёты D&D: это Card с соответствующим шаблоном/структурой. Ранее созданные карточки не классифицировать по тексту и не назначать им случайную inline-картинку как портрет. Дать явную команду добавить портрет к существующей Card.
- Тесты: создать шаблон персонажа, портрет и inline image одновременно, заменить/удалить портрет, семантическое сохранение, restart/backup/restore, два документа, missing/corrupt asset, разные DPI/размеры окна; старые шаблоны и карточки остаются доступными. Подготовить ручной сценарий.

## 6. Блок D — карта: сетка, единые токены (замечания 4–8)

Linear: ARU-77, после ARU-76. Сохраняем ARU-70/71, libvips, pyramid/cache и исходный raster coordinate space. Не начинать заново renderer.

### 6.1 Сетка

- Проверенная причина из кода: MapGrid.enabled по умолчанию false; GridLayer.paint прекращает рисование при cell_size × scale < 5 экранных пикселей. Визуальная проблема должна быть воспроизведена на реальной карте, а не объяснена только этим предположением. Проверить также z-order относительно тайлов, opacity/color, viewport, clipping и настройки.
- Для новых карт сетка включена по умолчанию. Существующие сохранённые настройки видимости сохраняются, если пользователь выключал сетку; предложить понятное включение одним действием. На панели карты видны переключатель сетки, прилипание (snap), размер клетки в пикселях исходной карты, смещение, контрастный цвет/прозрачность. Не прятать управление в глубокой форме. Сетка лежит между фоном и токенами, не дрейфует при zoom/pan/DPI/LOD. Линии читаемые на светлом и тёмном фоне, толщина в экранных пикселях.
- При отдалении, когда каждая клетка неразличима, использовать явно отличимую прореженную сетку (целочисленное кратное исходным клеткам) или другой измеренный способ отображения с пояснением; не рисовать миллионы линий. Визуальная детализация никогда не изменяет настоящую геометрию клетки и snap. Показ сетки и snap независимы.

### 6.2 Одна модель токенов, без маркеров

- Убрать команду «Маркер», PinItem и пользовательский отдельный тип маркера после безопасной миграции. Весь сценарий: добавить токен, выбрать изображение (или безопасная встроенная заглушка), тип «Персонаж»/«Предмет», имя, необязательная ссылка на Card; drag/drop, переименование, замена картинки, открытие/создание/отвязка связанной Card, удаление, Undo/Redo. Несколько токенов могут ссылаться на одну Card в разных местах/картах. Токен не копирует карточку. Графические маркеры-POI в новом UX тоже токены; не отдельная конкурирующая модель.
- Каноническая MapToken/TokenInstance содержит стабильный UUID, kind, title, необязательный image asset reference (placeholder при отсутствии), связь с Card/Entity, позицию в координатах исходного raster, размер в клетках, порядок отображения. Тип не выводить из названия/картинки. MapToken является объектом размещения, а не самостоятельным RPG персонажем или предметом.
- Персонаж: картинка обрезается по кругу с сохранением пропорций (center crop; пользовательская настройка кадра позже), белая контрастная рамка по окружности. Не рисовать квадратную рамку selection: отдельная индикация выделения не меняет тип/канонические данные. Предмет: изображение исходной формы/пропорций с alpha, без круговой маски и без постоянной рамки. Помещается в footprint с aspect-fit, не растягивается. Выделение должно быть видно для обоих типов. Круг — только персонаж (это уточнение к общему пожеланию о круглых токенах).

### 6.3 Геометрия размера

- Обычный токен занимает footprint 1×1 клетку. Предпочтительная модель: footprint_width_cells/footprint_height_cells (положительные целые для обычных и будущих больших размеров; 1×1 default), а не произвольно заданные независимые пиксельные размеры. Диаметр 1×1 персонажа равен размеру клетки с учётом рамки внутри bounding box. Предмет сохраняет пропорции внутри выделяемого размера. При изменении размера клетки визуальный footprint пропорционально меняется; zoom меняет только экранный масштаб, не world coordinates.
- Зафиксировать anchor convention и snapping в ADR, например позиция центра токена в raster pixels, snap по левому верхнему углу footprint к границам клеток, затем вычисление центра. Для 1×1 это центр клетки; для 2×2 — центр четырёх клеток, а не ошибочный центр одной клетки. Не допускать бесконтрольного смещения существующих токенов от изменения grid settings; изменение cell size не телепортирует токены, проверка/перепривязка выполняется явно либо через последующий drag. Для обычного размещения в режиме snap footprint целиком внутри доступной области; на краях обрезанной клетки определить однозначное правило. Не добавлять collision/initiative/gameplay.
- Старые MapToken.width/height в пикселях могут быть не кратны старой cell_size. В миграции не схлопывать автоматически крупные объекты в 1×1 и не терять размеры: сохранить legacy footprint/точные пропорции через версионированное переходное представление или доказуемую точную конвертацию, затем дать понятное явное приведение к клеткам. Новые токены создаются 1×1. Политику согласовать с владельцем, если она существенно меняет существующие размещения. Заложить контракт ≥2 клеток и тест геометрии уже сейчас; сложное UI настройки всех размеров не обязательно.

### 6.4 Миграция и проверки

- Старые MapPin нормализованы в [0,1], токены используют pixels. Мигрировать pin в token с прежним UUID/title/card_id и переводом `x * source_width`, `y * source_height` по реальным размерам исходного raster. Не угадывать размер при пропавшем фоне: безопасная отложенная миграция координат или явная диагностика с сохранением оригинала; никакой потери позиции. Предложенный default для legacy pin — item с нейтральной placeholder и без рамки; для существующего image token тип не выводить из названия, выбрать документированный default и возможность смены. Исходные изображения неизменны. После безопасной конвертации удалить legacy pin write/UI path; legacy чтение только для миграции.
- Проверить сохранение всех прежних ID, координат и связей, отсутствие pin+token дублей, неизвестный kind/version, rollback, повреждённые и пропавшие assets, две карты, undo/redo всех изменений, grid default и toggles, 1×1/2×2 footprint/edge/snap/offset, изменение cell size, zoom/pan/DPI, круглый clip, белую рамку, прозрачные предметы. Координаты не зависят от pyramid level. Тесты QGraphics geometry/paint с реальными изображениями; Windows ручные скриншоты на большой карте и измерения CPU/RSS/latency на прежнем профиле. Не выдавать синтетический benchmark за гарантию UX.

## 7. Блок E — многоколоночные таблицы (замечание 9)

Linear: ARU-78, после ARU-77.

### Контракт

- Равноправный Table document в общей иерархии. Своя структура: упорядоченные ColumnDefinition (UUID, name, data_type, position), RowRecord (UUID, position), значения ячеек по column_id/row_id. Схема и содержимое принадлежат Table, а не виджету. Стабильный ID не зависит от названия и индекса. Типизированные значения с различением пусто/null, число и строка. Минимум для итерации: текст, число, логическое значение (checkbox), контракт расширения на ссылки на Entity/assets в дальнейшем. Не строить формулы, rollups, arbitrary SQL, полноценную Notion-like систему или relations UI раньше согласования.
- Предпочтительно обычная SQLite-схема таблиц/колонок/строк/ячеек с FK и индексами, если подтверждает потребность в масштабировании; допустим versioned модульный payload с явным контрактом, если измерения показывают достаточность. Не оставлять tuple[str] и не делать SQL-таблицу физически на каждый пользовательский документ. Сравнить подходы в коротком ADR, учесть будущие фильтры, индексы, запросы и миграции; сохранить общий writer. Данные в канонической SQLite в обоих вариантах. Не дублировать схемы хранения.
- UI: настоящий grid/table view (предпочтительно QTableView/QAbstractTableModel), создание/удаление/именование/перестановка столбцов, строки, изменение порядка, редактирование ячеек и табуляция. Изменение типа колонки с проверкой существующих значений и явным подтверждением, если возможна потеря; удаление непустого столбца/строки подтверждается. Поддержать копирование диапазона/строки; по возможности безопасный paste TSV с валидацией. Ширины столбцов и сортировка представления — локальное состояние, не нужно тайно менять порядок строк.
- Случайная таблица остаётся полезной: выбрать равновероятно целую непустую запись, показать именованные столбцы и дать скопировать результат. Пустой считается запись, в которой все ячейки отсутствуют/пустые, а `0` и `false` — валидные значения. Без формул и весов в этой итерации. Пример: d100 encounter table со столбцами «Событие», «Описание», «Количество».
- Миграция старых RandomTable.rows сохраняет каждый текст (включая пустые), порядок, ID таблицы, создаёт один столбец «Вариант» и стабильные ID строк/столбцов; не фильтровать строки на миграции. Не терять редактирование активной ячейки при Ctrl+S, закрытии/смене проекта. Ошибку валидации показывать до записи.
- Проверки: три разных типа колонок, add/reorder/rename/delete, empty/zero/false, duplicate IDs, invalid types, random row selection, копирование, undo/redo или безопасная явная отмена разрушительных операций, независимые окна, old project migration, restart/backup. Нагрузочный профиль с десятками столбцов и тысячами строк; предоставить реальные измерения, не бесконечно создавать виджеты на ячейку. Не ухудшать Card editing и save pipeline.

## 8. Блок F — визуальные кубики и заготовки (замечание 10)

Linear: ARU-79, после ARU-78. Использовать настоящий DiceDocument из блока A.

- Основной интерфейс без необходимости писать выражение. Стандартные d4, d6, d8, d10, d12, d20, d100, рядом счётчики количества (0 по умолчанию или один d20 для новой заготовки), минус/плюс и ручной ввод количества; модификатор +/−. Выражение может служить дополнительным экспертным полем, не главным интерфейсом. Иконки и размеры убедительные, читаемые подписи. Пользователь может смешивать типы в одном броске.
- Кнопка «Бросить»; результат: значения каждого кубика сгруппированы по типу (например, d6: 3, 5; d20: 12), промежуточные суммы при необходимости, модификатор и крупный итог (3+5+12+2=22). Перебросить с прежними настройками, очистить количества, копировать результат. Отдельная ошибка при нулевом количестве или превышении разумного суммарного лимита. Никаких eval, симуляций бросков без действий пользователя, нового игрового rules engine.
- Именованные presets внутри DiceDocument: создать, переименовать, выбрать, изменять количества/модификатор, дублировать, удалить; сохранение между сеансами через общий pipeline. Начальные варианты для быстрого запуска: d20, 2d6, d100 (предложение, не жёсткий системный набор). Каждая запись preset имеет ID и независимую конфигурацию. Бросок не меняет сохранённый preset сам по себе. История бросков — текущая сессия (с ограничением размера), сохраняемая история/автоматический расчёт правил не входят в этот блок. Старый NdM±K сценарий сохранить, если поддерживается без двух несовместимых движков; расширить единый безопасный roller для смешанного набора.
- Вынести расчёт в pure domain с внедряемым RNG, UI получает результат, а не делает арифметику. Валидировать количество и стороны, суммарные ограничения и модификатор; каждая грань равновероятна. Проверить сохранение заготовок, смешанный бросок, d100, нулевое количество, отрицательный модификатор, слишком большой ввод, независимость нескольких DiceDocument и восстановление layout. Дизайн и реальные Windows скриншоты перед приёмкой.
