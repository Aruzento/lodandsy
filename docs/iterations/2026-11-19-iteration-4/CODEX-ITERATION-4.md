## 2. Порядок работы и экономия проверок

**Выполняй A → B → C → D → E → F → G.** Один функционально завершённый блок может содержать несколько согласованных задач Linear; не дели его на микроскопические циклы реализации/полной сборки. Сначала согласуй между собой общие контракты A/C/E/F, затем внедряй их по порядку. Не жди подтверждения этих ADR: границы уже утверждены.

Оптимизируй время разработки и тестов без снижения качества:

1. В начале сверяй состояние checkout и известные результаты CI. Один исходный контрольный полный прогон нужен, если исходная рабочая копия изменилась, baseline не подтверждён или обнаружена регрессия; не дублируй доказанно актуальный зелёный прогон неизменного коммита без причины. Зафиксируй, что проверил и что взял из CI.
2. Пока реализуешь логически связанную группу изменений, пиши тесты вместе с кодом и собирай их в целевые группы. Не запускай весь `pytest`, frozen packaging, smoke, benchmark или все линтеры после исправления каждой строки. Для синтаксической ошибки/правки теста используй только подходящую быструю проверку, если она нужна.
3. На границе A–F запускай одним пакетом тесты изменённых компонентов и ближайших зависимостей: domain, application, persistence, relevant Qt integration. Для структуры сущностей/формата, импортов, ссылок, операций с assets и writer обязательны целевые проверки целостности, отказов и восстановления. Полный промежуточный прогон допустим при большом межмодульном изменении или риске накопленной регрессии (в частности после смены базового контракта A/B или storage); обоснуй его, не делай механически после каждого исправления.
4. Если тест падает, установи причину, исправь и запусти конкретный упавший тест/связанный набор. Повтори более широкий набор после завершения исправлений, а не на каждый промежуточный diff. Не удаляй и не ослабляй действующие проверки ради зелёного результата. Тесты отменённых продуктовых контрактов можно заменить новыми, проверяющими актуальное поведение.
5. Профилируй тяжёлые сценарии пакетно: сравни baseline и готовый исправленный сценарий на одинаковых данных/окружении. Используй ограниченные управляемые нагрузки и фиксируй воспроизводимые команды. ## 3. Блок A — типы карточек и единая схема полей (фундамент CTV)

Linear: **ARU-80**, совместно с ARU-34/35/36/37/38/39, ARU-65, ARU-75/76. Цель — одна модель значений для карточки, Inspector, поиска и токенов; в будущем она пригодна для Variables/Ruleset без переноса данных из HTML.

- Раздели `Entity.kind` (вид документа) и `CardTypeDefinition` (содержательный тип карточки), а также `TemplateDefinition` (стартовое представление/компоновка). Тип и шаблон не одно и то же. Смена визуального шаблона не меняет тип и не стирает значения. Отдельные `FieldDefinition`, `SectionDefinition` и реестр поддерживаемых типов/секций; названия являются ориентиром, допускаются эквивалентные имена в стиле кода.
- Определение поля: стабильный машинный ключ, отображаемое имя, тип значения, область/группа, разумное default/unset, ограничения, подсказка отображения, возможность повторения только где действительно нужна. Типизированные значения хранятся в payload/подчинённых таблицах SQLite, не в HTML. Различай пустое/отсутствующее, 0 и false. Валидируй допустимость типов и чисел, сериализацию и неизвестные keys/version. Не исполняй пользовательские выражения.
- `Entity.title` остаётся единственным названием; `name`/«Название» — отображение/ключ доступа к нему, а не дополнительное хранилище. `description` и `notes` — реальные rich-text области/структурированные ссылки на секции, не копии текста в двух полях. Портрет/primary asset — одна типизированная ссылка. Унифицируй `summary`, `tags`, `aliases`, общие и типоспецифичные значения. Все изменения через единый application path с адресными уведомлениями по ID/ключу, Undo для операций, где он предусмотрен, и согласованным revision/dirty/save. Inspector и UI не владеют вторым набором значений.
- Минимальные встроенные поля: universal name/title, summary, description, notes, tags, aliases; character race, class_or_role, hp, ac, speed; item rarity, weight, cost; location region, climate, danger_level. Типы: текст, rich-text, число, bool, списки текстовых метаданных, ссылка на сущность/asset там, где используется. Числа с проверкой конечности/ограничений. Не вводи сейчас автоматические формулы, правила урона, обязательную механику D&D. HP и характеристики пока редактируемые значения канона, не независимые копии на каждой карте. Будущая отдельная runtime/campaign модель HP не входит в эту итерацию; оставь для неё явную границу, не плодя хранилища.
- Предусмотри отображение значения поля по стабильному ключу в UI-секции; не строить движок подстановок/произвольный синтаксис переменных. Встроенные шаблоны: пустая, статья, персонаж, локация, предмет. Реестр типов/шаблонов подготовь к дополнению встроенными типами (MOW vocabulary), без пользовательского конструктора схем. Не пытайся автоматически извлекать HP из свободного текста.
- Схемы и данные текущего проекта согласовать с последующими C/E/F. Зафиксируй ADR и новый актуальный storage contract, включая различие канона/представлений. Не требуй migration/legacy, если проще чистый тестовый проект.

Готовность A: изменение title/summary/hp через единый API отражается в читающих представлениях, round-trip всех поддержанных типов/пустых значений, отказ invalid key/type без частичной записи, сохранение общей иерархии и независимых документов; нет дублирования title/portrait/description. Проверить текущий backup/reopen для нового формата.

## 4. Блок B — редизайн интерфейса и структурированные карточки

Linear: ARU-26, ARU-75, ARU-76, ARU-33; использовать ARU-80. Цель — красивый редактируемый документ с информативной шапкой, а не техническая форма с панелью на всю ширину и портретом посередине пустого пространства.

- На основе текущего скриншота предложи и сам реализуй единый Qt design contract: тёмная сине-графитовая поверхность, сдержанные золотистые акценты существующей темы, читаемая типографика, плотные разумные отступы, ясные состояния hover/active/focus/disabled/error, контраст. Меньше избыточных контуров; осмысленные иконки и tooltip. Применяй семантические style tokens и общие примитивы к Tree/Inspector/Card Editor и затронутым панелям. Не перерисовывай заново все остальные модули без необходимости.
- Карточка: hero/header с названием, типом, тегами/aliases/кратким описанием и интегрированным портретом; ориентир MOW — hero block + media box + содержательные секции. Портрет нормального читаемого размера относительно документа, aspect-fit, выбор/замена/удаление контекстно; служебные alt/caption controls не должны занимать постоянно несколько полноширинных строк, доступны через настройку. Не повторяй заголовок в двух независимых полях. При узкой ширине адаптируй компоновку (портрет рядом либо выше), не создавай фиксированную гигантскую пустоту.
- Содержимое: реальное визуальное редактирование Qt HTML без видимых тегов; сохранённые rich-text возможности (шрифт, размер, цвет, заголовки, B/I/U/strike, lists, alignment, link/image, undo/redo). Сделай компактную панель действий, не перекрывающую документ; группируй/скрывай второстепенное в меню, сохраняй функциональность и горячие клавиши. Заголовки секций, пустые/редактируемые поля и читаемые значения не должны ощущаться как набор одинаковых форм. Локальная область свободного текста остаётся равноправной со структурой.
- Шаблоны из A отображают заголовки, поля, секции и rich-text области по контракту, а не размножают значения в HTML. Персонаж — портрет, summary, характеристики, описание, история/связи/инвентарь/заметки (пока текст или реальные поля/ссылки, без фиктивных игровых кнопок). Статья — читаемая структура; локация/предмет — собственные секции. Не заставляй все карточки иметь пустые громоздкие блоки. Сохрани визуальную ясность пустой карточки. Создание/редактирование поля из Inspector обновляет тот же документ и наоборот; метки типа могут отображаться в дереве, но не возвращай разделение по видам.
- Используй преимущества MOW как продуктовую идею: независимость типа и шаблона, теги/aliases, свободное содержание + типизированные данные, встроенный портрет. Никаких web engine, DOM widgets или исполнения MOW HTML. Переиспользуй собственные рабочие Qt resource protections, CardImages, WindowManager и механизм документного Undo. При разделении rich-text на секции не теряй текст, выделение, курсор и историю при переключении окон.

Готовность B: создание пяти шаблонов, изменение структурированного поля из обоих представлений, редактирование rich-text/inline image и портрета, save/reopen, несколько окон, dock/float/узкая ширина, клавиатура/DPI, нет дублирующих полей, нет служебной формы в качестве главного визуального результата. ## 5. Блок C — Card → TokenInstance, канон на карте

Linear: ARU-77, ARU-80, ARU-65. Цель — токен является размещением конкретной Card, а не независимым персонажем/предметом.

- Ровно одна Card для каждого `TokenInstance`; одна Card может иметь 0..N размещений на одной или разных картах. Идентификатор экземпляра отличается от card UUID. Экземпляр хранит map-local поля: ID, card_id, координаты в исходных пикселях/мировом пространстве, footprint в клетках, z/слой, при необходимости явно заданные presentation overrides (label/image/render kind). Map ID может задаваться владельцем коллекции; не дублируй его без нужды. Не хранить копии HP, названия, описания, характеристик карточки на экземпляре. Обычные правки канона видны всем экземплярам через адресное уведомление. Если оставляешь override, он явный, виден пользователю и сбрасывается к значению карточки; изменения канона не затирают override. Карточка содержит default token presentation; не надо заранее вводить игровые правила размеров.
- Начальный сценарий: перетащить Card из Tree на карту или выбрать существующую Card при добавлении; при создании нового токена с изображением сначала создать/выбрать Card, связь обязательна. Двойной щелчок открывает/фокусирует Card. Удаление размещения не удаляет Card. Удаление Card с размещениями — явное предупреждение с числом ссылок и подтверждаемая атомарная политика (предпочтительно удалить её размещения вместе с Card, без немых «бесхозных» токенов). Не удалять чужие Card по drag/undo. При неожиданной повреждённой ссылке показывай диагностику, не придумывай новую карточку. Проверить undo/redo и сохранение с учётом этой политики.
- Визуальные типы: `character`: круг, центрированный crop, белая рамка (выделение отличимо); `item`: оригинальная форма/alpha изображения, aspect fit, нет постоянной рамки. Значение по умолчанию берётся из Card type/presentation; портрет или явно назначенный token image — из assets карточки; отсутствие картинки отображается понятной заглушкой. Не копируй файл на каждый экземпляр.
- Размер: 1×1 клетка по умолчанию; предусмотрены целые кратные footprints, минимум 2×2/3×3 в проверках. При изменении cell_size отображаемый размер меняется вместе с клеткой. Snap на согласованных границах footprint, координаты независимы от zoom/LOD и сетка не перемещает существующие центры самопроизвольно. Сохрани существующее libvips-отображение больших карт. Не возвращай MapPin.

Готовность C: Card с портретом и несколькими экземплярами на двух картах; переименование/смена портрета обновляет все без копирования; независимые позиции/размеры экземпляров, удаление экземпляра/карточки, выбор/сброс override, drag/drop и переход к карточке, reopen/backup/Undo, отсутствующая картинка/битая ссылка диагностируется. Не реализовывать отдельное боевое состояние экземпляра сейчас; будущий state/campaign layer сможет ссылаться на ID экземпляра при необходимости.

## 6. Блок D — сетка и стабильность renderer

Linear: ARU-77. Проблемы: видимая толщина линий меняется при движении токена; на дальнем масштабе сетка слишком толстая. Не считай конкретную причину заранее доказанной только по жалобе.

- Воспроизведи при drag, repaint, pan, zoom, fractional transforms и DPR/mixed DPI. Проверь dirty regions/частичную перерисовку, порядок GridLayer/tiles/token items, косметические pen, raster alignment и антиалиасинг, накопление alpha/повторное рисование. Проверь, что линии не накладываются повторно на уже нарисованные области и не получают лишнюю толщину от world transform.
- Сетка в координатах карты, единый cell_size/offset; renderer отвечает лишь за визуальный уровень детализации. Близко — тонкая контрастная линия, далеко — облегчённая прореженная сетка, не толстая двойная рамка. Цвет/opacity/настройки остаются доступны. На больших zoom-out не менять математический шаг клетки/snap. Изображение и токены не должны сдвигать видимую сетку.
- Реализуй устойчивое обновление и тонкую ширину в экранных пикселях с учётом DPI (конкретный способ выбери по воспроизведению; допустим отдельный overlay pass или аккуратный QGraphicsView foreground/layer при сохранении правильного z). Не рендери бесконечное число линий: только видимая область с LOD. Проверить светлый/тёмный фон, зум, pan и drag. Не заменяй систему тайлов.

Готовность D: при неизменной camera трансформации последовательные redraw при drag не меняют пиксельную толщину линий; при далёком масштабе сетка тонкая, читаемая, без «плавания»; grid/world/snap остаются согласованы. По возможности добавить воспроизводимый offscreen image comparison/геометрический регрессионный тест, а не утверждать визуальную приёмку на основании числа линий. Ручной mixed-DPI сценарий в G.

## 7. Блок E — фундамент редактора карт и размещаемые assets

Linear: **ARU-81**, связана ARU-70/77. Цель — на существующей карте можно разместить дом/декор как asset независимо от токенов; модель допускает будущие линии/дороги/стены без переделки всех сущностей.

- Отдели фон/тайловый raster, `MapLayer`, `PlacedAssetObject` (вариант map object), `TokenInstance`, grid и состояние вида. Стабильные UUID слоёв/объектов; объект ссылается на общий проектный asset ID и слой. Координаты/размер/трансформация/порядок отрисовки не зависят от масштаба вида. Различай содержимое карты (persisted) и zoom/pan/выделение (view state). Не делай отдельную каноническую копию asset или Card.
- Базовый режим «Редактировать карту»: выбор/создание слоя, именование/порядок и видимость слоёв, выбор/импорт подходящего локального asset, размещение, выбор, перенос, изменение размера, удаление; Undo/Redo. Как минимум один полноценный рабочий режим размещения и редактирования объекта. Не превращай обычный drag токена в создание/перемещение декора. Обеспечь переход назад к работе с токенами и сохранение независимых операций.
- Предусмотри расширяемый минимальный geometry/object kind contract для будущих зданий/дорог, без реализации path editor, wall/light/object physics, сложных полигонов и процедурной генерации. Не нужно сейчас универсальное дерево классов на выдуманные виды объектов. В текущем MVP достаточно raster assets на слоях; дальнейшие типы геометрии должны добавляться через моделируемый контракт, не через переписывание persistence.
- Переиспользуй bounded media cache, asset adapter, общий writer, Qt renderer и тайлы; не декодируй фон целиком. Отсутствующий asset — заглушка/диагностика. Согласовать z-order и hit-test между grid, слоями, tokens/assets; блокировать операции с неподходящими объектами. Удаление/скрытие слоя не должно немо уничтожать содержимое; явная проверяемая политика. Учитывай несколько карт и большой объём.

Готовность E: импорт asset один раз, несколько размещений, два слоя и изменение видимости/порядка, движение/размер/удаление/undo, сохранение/reopen/backup, токены работают как раньше, сетка стабильна. Проверить новый inventory assets, закрытие во время загрузки, повреждённый ресурс, ограниченный расход памяти.

## 8. Блок F — однонаправленный импорт MOW

Linear: **ARU-82**. Цель — перенести карточки из MOW в новый формат LODANDSY, не запуская MOW и не поддерживая его формат в штатном редакторе. Используй приложенный реальный образец; анализируй доступный код/дополнительные файлы MOW при наличии. Не утверждай, что один образец покрывает все разновидности карточек.

Подтверждённая структура реального `.md`: YAML front matter `id: 24acd7ea-c76c-439c-af3c-5c46560fcaf0`, `schemaVersion: 1`, `updatedAt`, `contentHash`, `parent: 616fde79-87b4-4eaa-b6a1-bdeea740e9dd`, `order: 1790538099141`, `tags: [card, folder]`, `template: card`, `type: folder`, `aliases: []`; далее **HTML**, а не обычный Markdown. `.entity-layout.card-shell` (`data-card-shell="v1"`), `.entity-header`, `h1.singleline-field` с текстом «Существа.Тюрьма - подземка», `.card-short-description.rich-text-field`, `.media-box.is-portrait`, `.entity-main` и `.template-block[data-block-type="text"][data-block-version="1"]` с `h2` и `.rich-text-field`. Образец содержит runtime controls для tags/aliases/select/upload; их нельзя превращать в содержимое карточки. Type берётся из метаданных, а не из первого option в select. В данном образце портрет не выбран, краткое описание и body пусты, родитель в этом одиночном файле не предоставлен. Формат image references, wiki-links и других MOW блоков этим образцом не доказан.

- UI: импорт одной карточки или каталога карточек в текущий/новый проект (выбор места и явное применение), предварительная проверка и отчёт — сколько документов/ресурсов/связей распознано, конфликты, неопределимые ссылки, неподдержанные блоки. Разбор отдельно от применения; staging/транзакция с корректной очисткой при сбое. Исходный каталог только для чтения. Не перезаписывать существующие Card автоматически. Повторный импорт не должен silently удваивать/перетирать набор: идентичные source UUID обнаруживаются; при collision есть однозначный выбор skip/remap и отчёт. UUID mapping между внешними и внутренними сущностями, устойчивый порядок родителей/детей. Двухпроходный импорт: сначала распознай и выдели ID, затем восстанови иерархию/ссылки; отсутствующий parent → предложенный/явно обозначенный корень, не выдумывать parent; цикл/duplicate/corrupt input — диагностика без частичного разрушения проекта.
- Перенеси title, исходный type через mapping, tags, aliases, summary, description/body, поддержанные изображения/портреты и внутренние ссылки. Сопоставляй встроенные типы по `type`, а `template` отдельно. Для folder/creature/region/magic/skill/object/lore/note при отсутствии специализированного типа используй безопасный общий Card/fallback, не теряй сведения об исходном type в отчёте или структурированном метаданном. Типизированные поля только если их источник реально известен и валиден; не вычисляй статы из текста. Unknown blocks: безопасный текст/поддерживаемые фрагменты или идентифицируемый отчёт, не молчаливое исчезновение. Не импортируй старые UI inputs/select/buttons/data-runtime, HTML scripts/CSS, JS, события, внешний runtime, старый contentHash как доказательство целостности новой версии. Санитизируй rich text существующим whitelist; внешние URI/resources не загружать.
- Разбор YAML безопасный (без исполнения/опасных конструкторов, ограничить объём и глубину); если существующий parser недостаточен, выбор минимальной проверенной зависимости обоснуй и учти packaging/лицензию. Не меняй стек ради импорта. Пути изображений разрешай лишь внутри выбранного источника, проверяй нормализацию/symlink/junction/path traversal; import через общий assets API с проверкой размеров и дедупликацией. Не угадывай неуказанные пути, не ходи по сети. Если реальный формат media/links недоступен, реализуй проверенный generic безопасный путь и диагностируй неподдержанные варианты; не объявляй полную совместимость. Новые ссылки — `lodandsy://entity/UUID` через фактический mapping; разорванные/неоднозначные цели помечаются в отчёте. Не импортировать combat, tables/maps MOW 1:1, tasks, rules, history, campaigns.

Готовность F: реальный предоставленный файл открывается в новом Card UI с правильным названием/type/tags, пустым портретом, корректной диагностикой отсутствующего parent; runtime controls не видны. Проверить подготовленные помеченные fixtures для связанных карточек, порядка, конфликтов, отсутствующего parent/asset, повторного импорта, корректного rich text, опасных HTML/YAML/пути, rollback и save/reopen/backup. Отдельно перечислить реально проверенные форматы и ограничения; тестовые fixtures не выдавать за реальные MOW файлы. По возможности взять несколько реальных дополнительных образцов из доступного MOW. Если их нет, возможен дальнейший импортный тест владельцем, не блокируй выполнение G.

## 9. Блок G — техническая стабилизация и итоговая приёмка

Linear: ARU-75, ARU-78, ARU-54, ARU-45/46/47/52, ARU-70/77/81, ARU-63/64, ARU-79 (регрессии кубиков), ARU-66 (правила). Обязательные замечания независимого аудита не потерять при редизайне.

### G1. Изображения карточек — исправить, а не просто увеличить лимит

Подтверди проблему 8 MiB в актуальном коде. Реализуй ограниченный working set: видимые миниатюры/предзагрузка, вытеснение неиспользуемых, повторная подкачка при прокрутке, distinct pending/unavailable. Общий кеш и документ не должны бесконтрольно дублировать QImage; закрытые состояния документа не должны удерживать бесконечные изображения. Удаление inline image/Undo, смена проекта/asset invalidate корректно; не ломать QTextDocument Undo и canonical Qt HTML. Очередь ограничить, следить за одинаковыми запросами, stale callbacks и закрытием окна. При исчерпании бюджета валидное изображение не должно навсегда стать «недоступным». Проверить 5–20 разных изображений (в том числе thumbnails 1024²), последовательную прокрутку к каждому, возврат, несколько карточек, удаление/Undo, reopen, повреждённый файл, память. Доказать результат, не закреплять старый дефект тестом «доступны только два».

### G2. Таблицы/сохранение — измерить и подготовить адресное развитие

Сохранить текущие многоколоночные typed tables, UUID строк/столбцов, выбор целой строки, CRUD и текущие заготовки кубиков. Измерь типичный и 100k-cell workload: latency одиночного/серии edits, refresh/model reset, валидация, autosave/reopen, размер БД и GUI tick gap. Найди источники работы всего snapshot. Если локальная адресная валидация/notification даёт измеримую пользу без сложного пересмотра writer, исправь и сравни. Не внедряй новую ORM/СУБД или огромную переработку без необходимости. Полный переход на incremental SQL writer/ленивую загрузку — отдельное развитие при подтверждённом узком месте; зафиксируй конкретный контракт следующего шага и существующие/нужные Linear ID (без дубликатов). Не заявляй, что базы данных уже масштабируются произвольно. Проверь atomic multi-cell edits, typed values, invalid drafts, autosave, закрытие/открытие и backup.

### G3. Backup/restore — проверить ресурсы и ограничения

Проверить текущий 4 GiB суммарный бюджет, включая много больших карт, новые map objects, импорт MOW и inline/portrait media; проверить переносимость и восстановление с новой схемой. Замерить GUI block time. Проверить integrity/FK, no-overwrite, checksum, отказ при недостаточном месте/битых файлах, отсутствие зависимости от производной tile pyramid, исключение лишних временных данных. Синхронный backup признаётся временным: в этом пакете обязательно обеспечить корректность актуального формата и зафиксировать технический следующий шаг для фонового bounded backup/restore с прогрессом, отменой, disk-space checks и обоснованной политикой объёма. Не снимать предел простым увеличением числа без ресурсных гарантий. Не считать асинхронное копирование или поддержанный большой размер реализованными, если они лишь спроектированы; ARU-54 оставить открытой в такой части. Устрани обнаруженные локальные нарушения целостности в данной итерации.

### G4. Производительность карты

Раздельно замерь импорт/pyramid build, reopen, view pan/zoom, drag and repaint, autosave и event-loop gaps при активных картах. Используй прежний реальный крупный raster/бенчмарк при доступности, или явно описанный сопоставимый синтетический вход; 2 карты + до 1000 токенов, добавь representative placed assets и несколько слоёв. Сравни с доступным baseline, укажи CPU/RAM/DPI, размеры входов/сцены, p50/p95 и максимальный stall, RSS процесса GUI и worker, tile/cache disk usage. Раздели блокировки импорта/сохранения от собственно renderer. Устрани измеренные локальные bottlenecks в touched code; большие переработки только при обосновании и пределах пакета. Не выдавай предполагаемую плавность за ручную проверку и не обещай произвольный SLA.

### G5. Финальный контроль и передача владельцу

Проведи единый gate из раздела 2. Полный pytest/Ruff/pip check/diff; проверь интеграции Cards/Map/Tables/Dice, mixed tree, общую SQLite, ссылочную целостность, assets/backup, offline security, WindowManager lifecycle/docking/floating/layout и UI scaling. Убедись, что прежние технологии/устаревшие адаптеры реально удалены, а новые пакуются без дубликатов. Обнови `AGENTS.md`, `docs/MVP.md`, актуальные ADR (ссылки на заменённые решения), README и один отчёт итерации по результатам реальных проверок. Не создавай параллельный roadmap вне Linear. Сохрани исторические ADR как историю, а не действующий противоречащий контракт.

Собери финальный Windows ZIP/EXE с текущими pinned dependencies, целевыми Qt plugins и libvips, актуальными лицензиями. Проверь фактический frozen smoke, source parity, ZIP CRC/SHA256; назови точный путь артефакта. Чистая Windows без Python — отдельная ARU-64, не закрывай её по smoke на машине с установленным Python. При доступе к чистой среде проверь; иначе подготовь владельцу краткий чек-лист (включая кириллицу в пути, backup/reopen, mixed DPI). Сборку/приёмку не изображай успешно, если инструменты недоступны.

## 10. Итоговый пользовательский сценарий (чек-лист)

- Создать мир, карточку персонажа/предмета/статью; оценить цельный интерфейс, шапку, читаемость, portrait/summary, скрытие второстепенных контролов, узкие окна, DPI. Тип и шаблон не подменяют друг друга. Изменить поля Card/Inspector, проверить отсутствие дубликатов и обновление.
- Вставить 5–20 изображений, прокрутить все, изменить документ, Undo/Redo, переключить/закрыть/открыть окна, сохранить и открыть мир снова.
- Создать большую карту, разместить из Tree несколько токенов одной Card (на одной и двух картах), переименовать Card и заменить портрет, убедиться в обновлении всех экземпляров.
