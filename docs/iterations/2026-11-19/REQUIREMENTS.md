# LODANDSY — следующая итерация MVP: требования и приёмка

Редакция: 2026-11-19. Основа: пожелания владельца, аудит коммита `409da1e1e7095117f70ee88ebc140ebe491d5d6b` ветки `codex/mvp-cards-map-tools`, текущие задачи Linear и действующий `docs/MVP.md` в репозитории.

**Статус:** инженерная постановка на реализацию, а не утверждение о выполненной работе. Приоритет имеют новые продуктовые требования владельца. После проверки результатов обновить `docs/MVP.md` и нужные ADR. Не редактировать `main`, не делать commit/push/merge без прямого разрешения.

## 1. Цель, платформа и ограничения

LODANDSY — локальная Windows-first среда ведущего настольных RPG. Довести существующую реализацию до удобного рабочего инструмента: единое дерево объектов, редактирование и оформление Markdown-карточек с изображениями и шаблонами, действительно крупные карты, настраиваемая сетка и токены с изображениями. Сохранить работающие Cards, Map M1, Tools, Qt ADS docking, SQLite S3 и обратную совместимость проектов.

**Стек:** Python 3.14, PySide6/Qt Widgets, Qt ADS (проверять версии и совместимость); SQLite — один канонический источник данных, assets — отдельные относительные ресурсы; один SaveCoordinator/ревизии, переносимый локальный проект. Без нового web-стека, серверов, облака, ORM, плагинной платформы и полноценного VTT.

**Архитектурные границы:**
- `domain`: модели, инварианты, UUID и операции над данными без Qt/SQL;
- `application`: варианты использования, состояние сессии, координация модулей и сохранения;
- `ui`: Qt-виджеты, дерево, редактор, карта и взаимодействия;
- `SQLiteProjectStore`: сохранение и миграции, не вызывается напрямую виджетами;
- `WindowManager` — жизненный цикл окон; Qt ADS — размещение; не создавать параллельную систему docking;
- навигационное дерево отображает типы объектов, но не владеет payload; не смешивать карты/таблицы с `CardCollection` без принятого контракта общей Entity-модели;
- Card Markdown — канонический **текст**, просмотр не модифицирует его; утверждённый E2 (`Source / Preview / Split`), внутренние ссылки `lodandsy://card/UUID`; удалённые ресурсы в preview не загружаются.

**Оговорка про шрифты:** стандартный Markdown не выражает произвольные семейства, размеры, цвета выделенных фрагментов. Первая итерация включает разметку Markdown через панель и настройки шрифта/масштаба *отображения*, а не молчаливую конвертацию содержимого в HTML. Если нужен WYSIWYG с индивидуальными шрифтами отдельных фрагментов, сначала предъявить владельцу варианты редактора, формат хранения и влияние на обратимую сериализацию; без решения не менять канонический формат. Не блокировать этим независимые задачи.

## 2. Обязательный последовательный порядок

Перед стартом каждого блока: проверить актуальный HEAD/локальные изменения, относящиеся задачи Linear, соответствующие ADR и исходные тесты. После блока: тесты, ручной сценарий там, где доступен GUI, оценка побочных эффектов и отчёт. **Нельзя переходить к следующему, если оставлены неисправленные ошибки текущего блока.** Не выполнять параллельно конфликтующие изменения интерфейса и хранения. Если встретилось значимое продуктовое решение — остановиться только в его части, продолжить независимую работу и явно обозначить вопрос владельцу.

### Блок A — ARU-69 / 2.18: единое дерево и контекстная навигация

**Проблема:** карты и случайные таблицы открываются через верхние меню `Карты` и `Инструменты`, дерево — только Cards.

**Требуется:**
1. В фиксированной левой панели одно дерево проекта с разделами «Карточки», «Карты», «Таблицы» и быстрым доступом к «Кубикам» как инструменту. Внутри Cards остаётся вложенная иерархия. Для карт и таблиц отдельные элементы с названиями. Двойной щелчок/Enter открывает нужный объект по kind и ID через существующий application dispatch и WindowManager.
2. Контекстное меню у корня/разделов/объектов: создать, открыть, переименовать, удалить, а для Card — создать дочернюю, переместить, копировать ссылку. Для часто используемых операций — **действующие** кнопки возле выбранного/наведённого узла; не просто декоративные иконки. Обеспечить доступность без hover с клавиатуры и тачпада.
3. Создание карточки допускает выбор шаблона (в блоке D); до него сохраняется «Пустая карточка».
4. Сохранить fixed Tree/Inspector/rails, независимость открытых окон, drag-and-drop только там, где смысл определён (не смешивать DnD карточек и карт), selection/expanded/scroll при обновлениях, восстановление open docs, пустые состояния и обработку удаления открытой сущности.
5. Не оставлять дублирующие конкурирующие маршруты навигации: общие команды «Проект» остаются, дубли создания/обзора объектов в верхнем меню убрать или сократить после проверки существующих shortcut.

**Приёмка:** новая Card/Map/RandomTable создаётся в правильном разделе, отображается без перезапуска, открывается и фокусируется по ID; активные кнопки и контекстное меню работают; создание/удаление не ломают другие окна; состояние сохраняется после restart.

### Блок B — ARU-72 / 6.3: панель форматирования карточек

**Требуется:**
1. Компактная панель `Card Editor`: стиль абзаца (обычный / H1 / H2 / H3), жирный, курсив, зачёркивание, цитата, inline code, code block, маркированный/нумерованный список, разделитель, вставить ссылку, вставить изображение (интеграция с блоком C). У действий есть подсказки, доступные состояния и разумные сочетания клавиш.
2. Команды работают по выделению либо текущему абзацу в Source/Split; для режима Preview нужно переключить к Source/Split или сделать действия недоступными с объяснением. Не разрушать undo/redo, историю документа, курсор/scroll, пользовательские ссылки или оригинальный Markdown вне изменяемого диапазона. При повторном применении простого стиля он снимается, если это однозначно.
3. Шрифты/оформление: цельные согласованные типографические пресеты для просмотра (например, без засечек / с засечками / моно), настройка масштаба текста и читаемые H1–H3/цитаты/таблицы. Настройка отображения должна переживать смену режимов и перезапуск как UI state; **не изменяет Card.content**. Не пытаться незаметно сериализовать выбранные шрифты в HTML или терять их при `toMarkdown()`.
4. Поддерживать существующий E2 и строгую политику запрета сетевых ресурсов; preview не пишет в исходный Markdown.

**Приёмка:** с выделением и без него включить/выключить форматирование, undo/redo, preview/split и reopen; клавиатура и мышь, кириллица, сложные выделения, несколько редакторов, сохранение буквального Markdown без преобразований.

### Блок C — ARU-73 / 6.4: локальные изображения внутри карточек

**Требуется:**
1. «Вставить изображение» через файловый диалог; после этого — если не ломает основное поведение — вставка из буфера и drag-and-drop. Поддержать как минимум PNG/JPEG/WebP с проверкой формата/декодирования. Пользователь выбирает/задаёт `alt`.
2. Использовать **существующий единый путь assets**, относительный Markdown `![Описание](assets/<safe-filename>)`. Дедупликация по содержимому может быть реализована, если уместна в текущем адаптере; не использовать абсолютные пользовательские пути, `file:`, `http(s):` или новые непрописанные URI-схемы.
3. В Source видеть Markdown, в Preview/Split — изображение с корректным вписыванием в ширину окна без искажения пропорций. Изображение не должно вызывать сетевой запрос. Большие изображения отображаются через ограниченные миниатюры/декодирование; не приводить к гигантским `QPixmap` и зависанию UI.
4. Корректное сохранение/повторное открытие/backup/restore/перенос проекта, безопасные symlink/traversal, повреждённые и исчезнувшие assets, диагностика вместо пустого UI. Undo вставленного Markdown не удаляет разделяемый asset преждевременно.
5. Не переиспользовать плиточный движок карт там, где достаточно безопасного предпросмотра изображения внутри карточки; при необходимости общий слой управления assets допустим, если действительно уменьшает дублирование.

**Приёмка:** вставить фото в статью и карточку персонажа, сохранить, закрыть, открыть, скопировать проект на другой путь — фото остаётся, Markdown прежний; ссылку `http://` предпросмотр не загружает; исчезнувший asset даёт понятную заглушку.

### Блок D — ARU-74 / 6.5: шаблоны карточек

**Требуется:**
1. В процессе создания выбрать: `Пустая`, `Статья`, `Персонаж`, `Локация`, `Предмет`; дополнительно `Заметки сессии`, если UX не усложняется. Встроенные шаблоны на русском с полезной структурой заголовков, описаний, таблиц, полей-заготовок и блоков для изображений/ссылок.
2. Примеры разделов:
   - **Статья:** введение, основные сведения, история/детали, связи, примечания;
   - **Персонаж:** портрет, краткая роль, описание, особенности, биография, отношения, характеристики (свободный текст), инвентарь/заметки;
   - **Локация:** изображение/карта, описание, интересные места, персонажи, события, связи;
   - **Предмет:** изображение, описание, свойства, история, владелец, заметки.
3. Шаблон даёт стартовый **Markdown Card.content**, не создаёт новую жёсткую D&D `Character` модель, отдельную БД или обязательные поля. После создания копия полностью независима от исходного шаблона. Дальнейшее обновление встроенного шаблона не переписывает существующие Cards.
4. Создание работает как для корня, так и для дочернего узла; пустая карточка остаётся доступной. Переименование шаблона не меняет карточки. Существующую Card нельзя молча перезаписать применением шаблона.
5. Пользовательские шаблоны возможны в отдельном расширении. В этом блоке не строить шаблонный движок, дизайнер форм или полноценный справочник D&D; предпочтительны версионируемые Markdown-ресурсы с простым вызовом из application layer.

**Приёмка:** выбрать каждый тип, создать две независимые карточки, изменить содержимое, сохранить/перезапустить — шаблон не перестраивает данные; unknown template ID даёт ошибку без создания полупустой сущности; Card/Map ссылки сохраняются.

### Блок E — ARU-70 / M2.1: действительно большие карты

**Проблема:** `module_controller.read_map_image()` явно отклоняет изображения >16 000 000 пикселей или >64 MiB исходного файла; `MapView.set_image()` хранит полную QImage/QPixmap. Просто убрать проверки — небезопасно.

**Требуется:**
1. Прототип и короткий ADR выбора способа загрузки крупных растров: тайлы/пирамидальные уровни детализации, ограниченный кеш видимых тайлов, асинхронный импорт, прогресс, отмена, восстановление после прерывания. Исходный файл хранится в `assets`, производные тайлы — **перестраиваемый кеш** с версионированием (если другая модель не будет технически доказана). Никакого несогласованного нового формата канонических данных.
2. Панорамирование и масштабирование без декодирования всей карты для каждого кадра, без блокировки главного потока. Мировые координаты карты/маркеров остаются стабильными независимо от зума, тайлов и DPI.
3. Убрать произвольный барьер 16 млн пикселей только после ввода безопасной альтернативы; предусмотреть управляемые ресурсные ограничения и диагностируемый отказ на повреждённом файле/decompression bomb. Не обещать бесконечный размер, измерить фактические практические пределы.
4. Сравнить Windows-совместимые варианты Qt-only/подходящей внешней библиотеки; зависимости и лицензии — только по результату проверки. Не рассчитывать, что `QImageReader.setClipRect()` всегда экономит память: поддержка зависит от обработчика формата.
5. Проверить восстановление карты с существующими M1 markers, двунаправленные связи по UUID, импорт большого файла, несколько карт, ограничение памяти и кеша, Windows сборку. Документировать время импорта, панораму/зум и наблюдаемое потребление памяти на реальных измерениях.

**Приёмка:** карта существенно больше 16 MP импортируется и плавно просматривается на согласованном проверочном оборудовании без роста RAM пропорционально полной площади декодированного изображения в интерактивном режиме; существующий Map M1 проект открывается без потерь.

### Блок F — ARU-71 / M2.2: графические токены и сетка

**Требуется:**
1. На карте могут одновременно существовать **старые маркеры** и **новые токены**. Токен — самостоятельный объект с UUID, координатами в системе карты, ссылкой на изображение из `assets`, названием, размером (в клетках или мировых единицах), порядком отображения и необязательной связью с Card ID. Ссылка на Card не копирует её payload. Отсутствующий asset/удалённая Card сохраняют объект и дают диагностику.
2. Инструмент «Токен»: добавить/выбрать/переместить/переименовать/настроить размер/связать с карточкой/удалить, откатить/повторить. Выбор изображения из локальных файлов; использовать тот же безопасный ресурсный адаптер.
3. Отдельный слой **квадратной** сетки поверх карты: включить/выключить, размер клетки, смещение начала, прозрачность, необязательное прилипание токенов к клеткам. Сетка остаётся на месте относительно карты при pan/zoom и независима от тайлов. Удобный доступ через инструменты карты, без перегрузки окна кнопками.
4. Новые поля с версионированием схемы S3, безопасная миграция и обратная совместимость с прежним `MapDocument/MapPin`, backup/restore. Не начинать реализацию боевой системы, тумана войны, освещения, мультиплеера, правил D&D, измерительных инструментов без отдельного решения.

**Приёмка:** импорт токена с изображением, перемещение с включённым/выключенным snap, изменение размера сетки и zoom не меняет мировых координат некорректно; два токена на одной Card, отсутствие связанной Card, Undo/Redo, сохранение/перезапуск/backup/restore и открытие прежнего M1 проекта.

## 3. Общие проверки и завершение

- На каждом этапе: целевые pytest/pytest-qt, затем `python -m pytest`, `python -m ruff check .`, `python -m pip check`; не ослаблять старые тесты и не удалять сценарии без объяснения.
- После этапов B–D: полная регрессия Cards, links, images, selection/undo, focus и восстановление окон.
- После E–F: стресс-замеры и ручной Windows UX; UI GUI-thread не занят тяжёлым декодированием, отказ/отмена безопасны.
- Проверить версии и миграции SQLite, восстановление резервной копии и инварианты ID/revision. Не менять действующий проект напрямую ради тестов; использовать копию/фикстуру.
- После каждого блока дать краткий отчёт «что изменено → какие команды реально запущены → что прошло / не проверено → как проверить вручную → что в Linear → следующий блок». Обновить описание и состояния существующих задач Linear при действительных результатах, не ставить `Done` по факту написания кода.
- Итог: тесты и CI, Windows-дистрибутив, пользовательская приёмка. **ARU-64** (чистая Windows без Python, включая путь с кириллицей) остаётся отдельным обязательным открытым условием до фактической проверки новой сборки. Не считать это закрытым существующим зелёным CI.

## 5. Открытые продуктовые вопросы, которые нельзя решить молча

1. Нужен ли посимвольный WYSIWYG с собственным `font-family`, `font-size` и цветом внутри Card, несмотря на ограничение стандартного Markdown? Пока принят ограниченный стиль + типографика просмотра.
2. Должны ли шаблоны быть только встроенными, или уже в первой версии требуется редактор пользовательских шаблонов? Пока достаточно встроенных, без автопривязки Card к шаблону.
3. Точное визуальное поведение больших карт из ранее присланной ChatGPT share-ссылки недоступно из текущего веб-просмотра. Прототипировать только подтверждённые функции, не заявлять совпадения с неосмотренным референсом.
4. Нужно ли у токенов гексагональное поле, повороты, видимость игрокам? По умолчанию в этом блоке квадратная сетка и без VTT-правил.

Их можно вынести на утверждение владельца, не блокируя работу по независимым пунктам.
