# LODANDSY — контракт MVP, редакция 2026-11-18

Статус: согласованный контракт MVP; сквозная функциональная приёмка полной сборки подтверждена владельцем 18.11.2026. Полная сборка проверялась с установленным Python; запуск этой сборки на чистой Windows (ARU-64) ещё не подтверждён. Владелец подтвердил независимые документы по ID, Markdown E2, публичные ссылки и политику ресурсов, Map M1, Tools и хранение S3. Все обязательные ручные проверки W2 preflight пройдены владельцем; разрешённая миграция на Qt ADS выполнена. Итоговая готовность поставки требует также успешного CI и оставшихся проверок из раздела 8. План и состояния ведутся в Linear, этот документ — контракт результата, а не отдельный бэклог.

## 1. Продукт

LODANDSY — локальная рабочая среда одного ДМа: подготовка материалов мира и ведение игры. Пользователь создаёт и редактирует карточки, размещает связанные объекты на карте, пользуется доступными инструментами, держит нужные документы рядом и возвращается к миру после перезапуска. Работа без аккаунта, сети и стороннего сервера. Windows-first, нативный интерфейс. Карточки, Map и Tools — три системы целевого первого релиза; объём каждой для MVP ограничен ниже. Не путать ранний рабочий срез Cards с готовым трёхсистемным MVP.

## 2. Пользовательский интерфейс (подтверждённая рамка)

- Основное окно AppShell, фиксированные LeftRail/RightRail, Tree слева и Inspector справа; панели не превращаются в свободно перемещаемые документы. Рабочая область между ними; рабочие окна Card Editor, Map, Tools отделены от панелей.
- Открытие карточки из Tree двойным щелчком; подтверждённая политика: один документ по ID, повторное открытие фокусирует его, другие карточки открываются отдельно. Выбор B не переназначает окно A. Inspector показывает текущую выбранную сущность, активный документ — самостоятельный контекст. При желании отдельный follow-selection режим обсуждается позже.
- Рабочие окна свободно перемещаются, закрепляются сбоку/сверху/снизу/в центре, поддерживают разделение и вкладки там, где это соответствует оконному контракту; вставка между двумя окнами и между окном и фиксированной панелью раздвигает соседей. Подсветка цели соответствует фактическому размещению. Floating — реальные рабочие окна с системным поведением; максимизация, восстановление на точке захвата, перенос между мониторами, возврат в dock, закрытие/повторное открытие. Не допускать схлопывания центральной зоны и недоступных целей.
- Сохраняются открытые документы, размещение и размеры; если экран исчез, вернуть окна в видимую область. Состояние UI отдельно от данных мира.
- Визуальное направление navy/black, сдержанное золото Art Deco, единые токены, читаемые шрифты, согласованные SVG-иконки; не перегружать декором. Все hover/focus/selection/disabled/error состояния различимы, масштабирование Windows и кириллица корректны. Не подменять системные заголовки floating декоративными ради красоты.

## 3. Cards — основной рабочий сценарий

- Создание корневых/дочерних карточек, переименование, изменение содержания, изменение родителя и порядка siblings, drag-and-drop, каскадное удаление с явным подтверждением. Структура хранится в домене, а не в Qt-строках. Запрещены неизвестные родители, циклы, дубли ID, некорректные заголовки. После удаления выбранного документа определённое пустое состояние или безопасный переход; закрытие/инвалидация удалённых документов без потери остальных.
- Tree сохраняет выбранный ID и раскрытие при rename/create/move; Inspector показывает ID только для чтения, title и parent с валидацией. Карточки имеют свободный Markdown-текст, а не обязательную D&D-форму. Утверждённый UX первого релиза — source/preview/split (E2); preview не перезаписывает Markdown. Ссылки по стабильному ID, понятная диагностика broken links, переход по ссылке без разрушения другого открытого контекста; базовый поиск по заголовку и содержимому.
- Несколько независимых Card Editor; сохранение Undo/Redo, курсора и прокрутки по документу в течение сессии, изменение имени/текста отражается во всех открытых представлениях. История Undo не обязана переживать перезапуск, если не согласовано отдельно. Документы не дублируются как канонические данные.
- Модель: id, kind, title, parent_id, position, card.content. Версия формата, ревизия и timestamps — инфраструктурные поля, если приняты контрактом хранения. Не строить наследование всех игровых сущностей, пока есть только Card. Tree использует EntitySummary. Неизвестный kind безопасно диагностируется без удаления payload.

## 4. Хранение — утверждён S3 (18.11.2026, ARU-40)

Одна каноническая SQLite на проект; стандартный sqlite3 без ORM. Исходный Markdown и стабильные UUID сохраняются без преобразования. Отдельные изображения/вложения используют относительные пути. JSON по сущностям и параллельный файловый формат не поддерживаются. Предусмотреть экспорт Markdown на будущее, не реализовывать его в MVP. Решение и сравнение: [ADR-003](adr/003-storage-comparison.md).

- Создать/открыть локальный Project и переносить папку без абсолютных путей. Данные Cards, Map и Tools имеют одного владельца; предметная модель и UI напрямую не зависят от SQL.
- Составные операции выполняются транзакционно. Foreign keys включены для каждого соединения. Иерархия без циклов, стабильные ID и порядок валидируются в домене. Ссылки маркеров на Card допускают предусмотренные продуктом разрывы и не становятся обязательным FK, уничтожающим маркер.
- Один SaveCoordinator: snapshot + revision, debounce autosave, Ctrl+S тот же путь; подтверждённая запись снимает dirty только для сохранённой ревизии, старый save не перезаписывает новый. Поиск/FTS, если добавлены, производны от канонических данных.
- Assets записываются согласованно с публикацией ссылок в БД; прерывание не создаёт подтверждённых ссылок на неготовые ресурсы. Резервное копирование и восстановление охватывают согласованную БД и assets. Версионирование схемы, безопасные миграции и backup перед изменением существующих схем.
- Один писатель, защита от второй открытой копии; сетевой диск/cloud-sync не обещаются. Видимы clean/dirty/saving/error, retry и предупреждение о несохранённом при закрытии; ошибка не сбрасывается молча. Неизвестная будущая версия/неизвестный kind безопасно диагностируются без изменения данных. Повреждение не приводит к автоматическому уничтожению валидных данных.
- Настройки layout, позиция камеры и выбор не входят в содержимое мира: отдельный `.lodandsy-ui.json`, с версией и безопасным fallback. Повреждённый/будущий UI-файл сохраняется перед заменой; данные мира не переписываются из него. При исчезновении монитора окна возвращаются в доступную область.

## 5. Map — утверждённая граница MVP (M1)

Принят M1: атлас связанных знаний, а не боевой VTT. Создание нескольких именованных карт и открытие в рабочем окне; импорт локального изображения в assets, pan/zoom, создание/перемещение/переименование/удаление pin, привязка к существующей или новой Card, открытие карточки из pin, сохранение и восстановление. MapDocument имеет собственный ID и данные карты; MapInstance имеет отдельный ID, координаты и необязательную ссылку на Entity, не копирует её содержимое. Одна Card размещается несколько раз и на разных картах. Удалённая ссылка не уничтожает геометрию; отсутствующий asset отображается как placeholder с диагностикой. Простая авторская подпись допускается как явный override. Проверить undo для редактирования объектов.

QGraphicsView/QGraphicsScene выбран после ограниченного измерения (ADR-006). Изображения PNG/JPEG/BMP/GIF/WebP до 16 млн пикселей / 64 MiB; кеш декодированных QImage 64 MiB. Импорт и decode — в worker pool, виджеты — в GUI-потоке. Открытые сцены дополнительно удерживают QPixmap; большие наборы открытых карт требуют измерения памяти. Не добавлять tiles/GPU renderer до измеренной необходимости. Сетка, токены, измерения, слои M2 — только после выбора владельцем конкретного сценария; vision, fog, lights, multiplayer, боевые правила — не MVP.

## 6. Tools — утверждённая граница MVP

Приняты dice roller + редактируемые random tables, копирование результатов. Кубики: ограниченный проверяемый синтаксис вроде NdM±K, валидация, результат каждого кубика, итоговая сумма и повтор броска, без eval; тестируемый источник случайности. Таблицы: создание, строки, выбор случайной строки, сохранение между сеансами в данных модуля. Инструменты открываются рядом с Card/Map и не меняют их данные напрямую. Не строить внешний SDK, загрузку произвольных плагинов и универсальные правила D&D. Результат можно копировать; автоматическая вставка, история бросков, веса строк и таймеры — только по согласованному контракту.

## 7. За границами MVP

Аккаунты, синхронизация, сервер, web/mobile-клиент, AI, multiplayer, полноценный VTT, боевая система, движок правил и эффектов D&D, сложные типы Character/Item, Campaign System, графовые доски, большие географические карты, внешний plugin SDK и автоматические обновления. Рабочий проект мира не равен Campaign System. Не добавлять новые технологии ради воображаемых будущих задач.

## 8. Критерии готовности и приёмки

- Cards: создать A/B, вложить B, переименовать, переместить, изменить порядок, переключаться между документами, проверить сохранение выбора/раскрытия, Undo, ссылки и поиск. Отклонить цикл и некорректный ID. Удаление поддерева — только подтверждённое; ни одной висячей иерархической ссылки.
- Workspace: одновременно открыть 2 разные карточки, карту и инструмент; изменение A не меняет документ B; dock/split/tab/insert/float соответствуют подсветке; проверить два CENTER, Escape, resize, maximize→drag, два монитора и смешанный DPI, фокус, закрытие и повторное открытие. Перезапуск восстанавливает layout, отключение монитора не делает окно недоступным.
- Данные: создать проект → редактировать → autosave/Ctrl+S → закрыть → открыть = идентичные данные, ссылки и положение объектов. Проверить ошибки записи (права, место, имитация прерывания), порядок ревизий, частичный сбой удаления, backup/restore, миграции, перенос папки, отказ второй копии. Производный поиск, если добавлен, должен перестраиваться из SQLite. Содержимое не теряется или ошибка однозначно предупреждает о неподтверждённом сохранении.
- Map (если принято M1): импорт → pin → Card → изменение → сохранить → открыть снова; две точки с одной ссылкой; битая ссылка и отсутствующее изображение диагностируются. Tools (если приняты): корректный/некорректный бросок, сохранение таблицы, повторное открытие; инструменты не ломают Cards/Map.
- Производительность: широкое и глубокое дерево, обход потомков через индекс, без повторного полного сканирования для каждого потомка. Предлагаемые нагрузочные профили 10k обычный / 50k стресс, не SLA; зафиксировать условия, время и память, обосновать пределы карты и кеша. Не выдумывать показатели.
- Поставка: воспроизводимые зависимости, CI test/lint, Windows-дистрибутив с Qt plugins; запуск на чистой Windows без Python, с кириллицей в пути, открытие/сохранение мира, docking, лицензии и отсутствие потери мира при обновлении/удалении приложения. Никаких заявлений о готовности, пока обязательные проверки не пройдены.

## 9. Как использовать существующий Linear

Проверено 18.11.2026: `P-ARU-2` (1) завершён; `P-ARU-3` (2) в работе; `P-ARU-4…9` (3–8) запланированы. Состояния перенесены из более раннего Trello и требуют сверки с checkout. Не менять нумерацию и не закрывать задачи автоматически.

Зависимости для исполнения крупными блоками:

1. База документов и окна: существующие 2.9 (ARU-19), 2.9.4 (ARU-23), 2.12–2.17 (ARU-28…33), 3.1–3.6 (ARU-34…39), 5.1 (ARU-55). Провести ограниченный оконный прототип раньше расширения custom docking; защитить инварианты, единый write path, selection/expanded state и устойчивые документы. Сверить 2.9.x, тему 2.10 и ADR 2.11. Не дублировать работу уже покрытую тестами.
2. Сохранение: ARU-40 (4.0) — решение владельца, затем ARU-41…54 (4.1–4.14), пересогласовать задачи при смене storage. Сделать полный цикл сохранения до Map и Tools.
3. Рабочее пространство и Cards: ARU-56…58 (5.2–5.4), ARU-59…60 (6.1–6.2), закрыть связанные недоделки этапа 2. Ранний Windows build проверить до слишком дорогой интеграции docking.
4. Map и Tools: после утверждения границ добавлены ARU-67 (Map M1) и ARU-68 (Tools), без дублирования существующих задач. Не смешивать с 8.1 (ARU-65) — будущая игровая модель, не полноценный игровой движок в MVP.
5. Поставка: ARU-61…64 (7.1–7.4), итоговая сквозная приёмка. Допускается ранний технический срез сборки в связи с 5.1 без изменения плановых номеров.

Это порядок зависимостей, а не новый глобальный план. Codex должен сверить текущие состояния и предложить перестановку владельцу при необходимости.

## 10. Принятые решения и условия дальнейшего развития

1. Окна: принят W2 после сравнения W1/W2 и ручного preflight владельцем; PySide6 6.11.2 + PySide6-QtAds 5.1.1. ADS владеет layout, WindowManager — lifecycle, domain не зависит от ADS. Фиксированные панели остаются в AppShell. Обновление пары библиотек требует повторной проверки.
2. Формат хранения S3 принят 18.11.2026 (ARU-40): каноническая SQLite + assets, sqlite3 без ORM. Внешнее редактирование и экспорт Markdown не входят в MVP. Параллельный S1 не реализуется.
3. Markdown E2: утверждён `[Название](lodandsy://card/UUID)`, UUID в текущем проекте; label независим от переименования цели. Открыть/фокусировать целевой редактор, сохранив исходный. Удалённая цель, некорректный UUID и unknown kind диагностируются. Команда копирует готовый Markdown с экранированием. HTTP/HTTPS — только явная активация в системном браузере; preview не загружает сеть, удалённые картинки заменяются текстом. Локальные изображения — только внутри assets текущего проекта без выхода через traversal/symlink. Другие схемы блокируются, source не меняется. Контракт: ADR-005.
4. Map M1 утверждён 18.11.2026; сетка, боевые токены, измерения, сложные слои, fog/lights и multiplayer не входят в MVP.
5. Tools утверждены 18.11.2026: NdM±K с деталями каждого кубика и суммой; пользовательские таблицы в проекте, случайный выбор строки и копирование результатов. Автоматизация правил и внешний SDK не входят в MVP.
6. Подтвердить нагрузочный профиль и визуальные референсы при наличии. Inspector следует за выбором Tree, открытые документы сохраняют контекст (подтверждено 18.11.2026). Не блокировать исправление общих инвариантов и baseline этим списком.
