# ADR-004: реализация S3 и сохранения

Статус: реализация решения владельца S3 от 18.11.2026, автоматические проверки пройдены;
владелец подтвердил ручной цикл save/restart и backup/restore полной сборки.
Проверка полной поставки без Python остаётся открытой. ARU-39–54. SQL находится в application-адаптере,
domain и ui не содержат запросов к БД. ORM и новые зависимости не добавлены.

Одна папка проекта содержит project.sqlite3, assets/ и служебный .lodandsy.lock.
Метаданные и revision находятся в БД, параллельного JSON manifest/entities нет.
SQLite schema version 1 содержит metadata, entity и asset; version 2 добавляет индекс
entity_parent_position. Version 3 добавляет map_document и random_table с versioned
payload в SQLite (pins/rows — JSON-значения внутри БД, не параллельные файлы).
Map asset_id имеет FK на asset; pin.card_id — стабильный UUID без FK, поэтому удаление
Card оставляет broken link. Начальные поля entity: UUID, kind=card, title, parent_id,
position, payload_version=1, исходный content. Порядок задаётся упорядоченным индексом
детей в домене, в snapshot сериализуется порядковыми целыми по каждому parent.

При открытии сначала проверяются schema version, quick_check, FK, kind/payload version,
UUID/title, позиции, родители и циклы. Unknown/future/corrupt данные приводят к отказу
без перезаписи контейнера. Для v1→v2 перед изменением создаётся согласованная SQLite
копия в backups/, затем явная транзакция DDL и PRAGMA user_version. Переход v2→v3
также создаёт backup и выполняется транзакционно; v1 проходит оба шага одной
транзакцией. Assets не изменяются. Ошибка откатывает DDL и версию, backup остаётся.
Повторное открытие текущей схемы идемпотентно. Новые версии требуют своих миграций.

SaveCoordinator получает неизменяемый снимок и номер revision в GUI-потоке. Один
ThreadPoolExecutor writer записывает снимки последовательно; каждое соединение
создаётся в рабочем потоке, foreign_keys=ON и synchronous=FULL. Измерение 10 000 Cards
по 1 КиБ на локальном temp дало 115.58 мс на save, поэтому SQLite I/O вынесен из GUI.
Qt-результаты применяются queued signal в GUI-потоке. Нет доступа к виджетам из writer.
Autosave debounce 750 мс и Ctrl+S используют этот же путь. Ctrl+S/закрытие ожидают
результат через Qt event loop; подтверждение снимает dirty только для записанной
ревизии. Более новая правка остаётся dirty. Reentrant flush отклоняется. Ошибка
сохраняется видимой до успешного retry. Смена проекта/закрытие ждут текущую запись,
writer lease не освобождается во время операции.

Транзакция сохранения валидирует snapshot, проверяет monotonic revision, заменяет
согласованный набор entities/assets/maps/tables и обновляет revision одним commit. Повторная или
старая revision не перезаписывает более новую. Один писатель защищён OS file lock;
аварийный выход освобождает lock, оставшийся служебный файл не считается блокировкой.

Ресурсы неизменяемы: импорт копирует данные во временный файл, fsync, atomic replace,
затем запись asset metadata разрешается в следующем общем snapshot. Ошибка/прерывание
до commit оставляет максимум невостребованный ресурс, а не подтверждённую ссылку на
неполный файл. Автоматического удаления orphan-файлов нет. Относительные пути
проверяются и не могут уйти из проекта. Уже отсутствующий сохранённый ресурс остаётся
в metadata для диагностики; новый отсутствующий ресурс не публикуется.

Резервная копия .lodbackup — ZIP с согласованным SQLite backup API snapshot и всеми
файлами внутри assets, включая вручную добавленные и ещё не зарегистрированные,
на которые может ссылаться Markdown. Размер/хеш зарегистрированных ресурсов проверяются также
во время копирования. Копия публикуется atomic replace; ошибка оставляет прежний
файл копии и проект. Восстановление проверяет inventory, пути, symlink entries, CRC,
ограничение 4 GiB, БД и хеши в staging, затем переносит staging в новую папку.
Существующая папка никогда не заменяется. Это backup контейнер, не второй канонический
формат работы. Версионные DB-копии перед DB-only миграцией используют неизменённые
assets существующего проекта, не объявляются переносимым архивом всего мира.

Ограничения: не проверены реальный power loss/полный носитель/права на чистой Windows;
ошибки записи и откат проверены инъекцией отказов. Map import/decode выполняются
в ограниченном worker pool, результат применяется в GUI; Qt-виджеты из worker
не изменяются. Большие backup/restore пока синхронны; их длительность зависит от
размера ресурсов, это ограничение кандидата. Ленивый SQL payload
и FTS не реализованы: поиск работает по canonical in-memory состоянию, без второго
хранилища. Сетевые диски и cloud-sync не обещаны. Layout и камера не входят в БД мира.
Пересмотр при измеренной необходимости incremental save, новом типе данных или иной
семантике assets; смена формата требует согласования владельца.

Историческое расширение формата Actor/rules: ADR-033 (SQLite15).
Действующая база совместимости и обязательная процедура последующих миграций
определены в [ADR-040](040-managed-projects-v001.md).

## Дополнение 27.11.2026 — запись изменённых агрегатов

Действующий путь Architecture & Stability S4 заменяет полную перезапись из
исторического решения. SaveCoordinator передаёт писателю полный неизменяемый
снимок, его целевую ревизию и последнюю подтверждённую SQLite-ревизию. Серийный
номер EntitySession имеет своё назначение. Несколько правок до autosave,
дополнительные изменения reconcile и регистрация вложений входят в целевой снимок.

Под существующей блокировкой писателя и `BEGIN IMMEDIATE` проверяются файл,
схема, UUID проекта, ревизия, `quick_check`, внешние ключи, версии и состав
payload. Сохранённые данные декодируются один раз. Совпадение всех типизированных
значений с проверенной ревизией позволяет переиспользовать её доменную проверку.
При расхождении писатель отказывает в записи. Целевой снимок целиком проходит
доменную проверку. Открытие, миграции и восстановление сохраняют полную проверку.

Изменения оболочек Entity и payload определяются по UUID. SQLite обновляет
только затронутые оболочки, Card с Actor, Map с токенами, Table со строками,
столбцами и ячейками, метаданные активов, правила и экономику. Изменение
порядка учитывает все затронутые Entity. Связанные записи удаляются до вставки
в затронутых агрегатах, чтобы атомарно переносить UUID между владельцами.
Связанные родительские строки обновляются через `ON CONFLICT DO UPDATE`.
Обновление ревизии и запись данных образуют один SQL-коммит.

Писатель держит в памяти последний проверенный снимок и цель попытки,
результат которой может быть неизвестен. После ошибки он перечитывает
фактическую ревизию до любой новой записи. Точный ранее применённый снимок
подтверждается без DML. Новая цель после потерянного ACK сравнивается с
фактически сохранённым снимком. Повтор со старой ревизией или чужим состоянием
получает отказ. Поздний Qt-результат сверяется с активной задачей, а при потере
сигнала координатор сам забирает завершившийся результат. ACK для N оставляет
более новые изменения dirty. При переключении и закрытии писатель завершается
до освобождения блокировки. Интерактивное ожидание имеет свой таймер опроса.
При завершении координатор ждёт рабочий поток напрямую и обрабатывает его
результат на GUI-потоке, даже если доставка Qt-событий уже остановилась.

Map10 сохраняет проверенную резервную копию до первой конвертации. После
восстановления используется проверенный снимок открытого мира. SQLite17,
Card8, Map9–10, Actor1, Table4, Rules1 и Economy1 сохранены. Полная запись
остаётся тестовым режимом той же транзакции с теми же кодеками.
