# ADR-040 — Управляемый каталог и совместимость v0.01

Решение владельца от 26.11.2026, ARU-44, ARU-53, ARU-54, ARU-66. Заменяет
часть ADR-030 о поиске и размещении миров и прежнее правило совместимости на
этапе прототипирования.

## Каталог и переключение

- `ProjectCatalogue` получает системный Documents через
  `QStandardPaths.DocumentsLocation`. Только прямые папки в
  `LODANDSY/project/` участвуют в обнаружении. Диагностика появляется у
  каталогов с ожидаемым файлом мира или маркером блокировки.
- Имена проверяются по правилам Windows. Ограничение в 200 единиц UTF-16 для
  абсолютного пути оставляет место для служебных файлов старых Win32-путей.
  Сравнение имён выполняется без регистра. Публикация идёт под блокировкой
  каталога через staging и переименование без подмены существующей папки.
  Временные каталоги доступны только операции, которая их создала.
- `ProjectHistory` хранит локальное время успешного открытия в UTC и путь
  последнего диалога. История задаёт порядок и подписи в Welcome и Open.
  Внешние миры можно открыть явно. Они остаются в исходных папках.
- ProjectController подтверждает переключение, но сбрасывает текущий мир и
  его черновики после проверки нового. Повторное открытие уже выбранного мира
  ничего не меняет. Writer lock проекта действует отдельно от блокировки каталога.
- Restore использует действующий `.lodbackup` pipeline. Перед извлечением
  проверяется свободное место под заявленный распакованный объём. Остальные
  проверки выполняются в staging. Принимаются только новые имена.

## База совместимости

Операционное обозначение приложения — **v0.01**, упаковочные метаданные Python —
`0.1.0`. В данном кандидате нет изменения канона и миграции.

| Слой | Текущая версия |
|---|---|
| SQLite `PRAGMA user_version` | 17 |
| Card | 8 |
| Map | 9 при записи, действующие декодеры SQLite17 читают 7/8 |
| Actor | 1 |
| Правила проекта | 1, профиль D&D 5e 2014 версии 2 |
| Table | 4 |
| Экономика | 1 |
| Локальная раскладка | 4, отдельный файл |

Для каждого изменения формата поддерживаемого мира необходимо:

1. Определить версию до открытия на запись и подтвердить путь перехода.
2. Создать и проверить резервную копию до исходной записи. Обеспечить совместимость
   копии с фактическими приложенными файлами.
3. Применить последовательные миграции, сохранив UUID, связи, содержимое и вложения.
4. Проверить новый формат, ограничения SQLite, ссылки и целостность данных.
5. Проверить повторное открытие с актуальной версией без повторной миграции.
6. Покрыть ошибки каждого шага. Транзакция достаточна для отката только операций
   внутри SQLite. Если меняются файлы, нужен безопасный перенос копии или
   проверенный откат обеих частей.

Неизвестная новая версия отклоняется до получения writer lock. Неподдерживаемые
прототипы до v0.01 получают диагностику. Исходные файлы сохраняются в обоих случаях.

После базового кандидата ARU-77 добавляет Map10 в SQLite17. При открытии Map7–9
миграции на диске нет. Переход начинается при записи дробной геометрии или угла
токена и использует проверенный `.lodbackup` до изменения прежних данных.
