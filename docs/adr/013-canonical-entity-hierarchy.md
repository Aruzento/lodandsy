# ADR-013 — каноническая смешанная иерархия документов

19.11.2026, итерация 3, ARU-34/35/36/37/38/39. Продуктовая граница прямо изменена
владельцем в пакете REQUIREMENTS итерации 3. Заменяет группировку и Card-only DnD
ADR-007; остальные оконные решения ADR-001/002 сохраняются. Ручная Windows-приёмка
этой итерации ещё не проводилась.

Контекст: UI-группы прежнего кандидата отражали три независимых хранилища идентичности;
удалить только заголовки Tree недостаточно для межтипового parent/reorder/delete.
Варианты: параллельное дерево UI; перенос модулей в CardCollection; общий envelope с
типизированными payload модулей. Выбран последний, согласно новому контракту владельца.

`Entity(id,kind,title,parent_id,position)` — единственная каноническая структурная запись
Card/Map/Table/DiceDocument. `EntitySummary` — совместимое имя того же immutable типа.
EntityCollection владеет одним лесом, индексом детей и одной редакцией payload на ID;
модули определяют типы payload и операции над ними. Домен не зависит от Qt, SQL или ADS.
Загрузка проверяет весь лес, UUID, точный sibling order и межтиповые циклы; изменения
проверяются до мутации. Удаление и обход глубокого поддерева не рекурсивны.

CardCollection теперь адаптер карточек к общему реестру, не владелец карт/инструментов.
Card/MapDocument/RandomTable/DiceDocument возвращаются как immutable проекции envelope
и payload для существующих редакторов. Кеш проекции производный, проверяется по
идентичности исходных immutable значений и удаляется с сущностью; отдельной изменяемой
копии мира нет. Map payload и операции по-прежнему определяются модулем карты.

S3 schema 5: `entity` содержит только пять общих полей. `card_content`, `map_document`,
`random_table`, `dice_document` ссылаются на общий ID через FK; title/parent/order в payload
не дублируются. Card payload остаётся исходным Markdown версии 1; публичный rich-text
формат в этом блоке не вводится. Map pins/tokens/grid и ресурсы не преобразуются.
Один ProjectSnapshot/writer/revision обслуживает autosave и Ctrl+S.

Миграция 1–4 → 5: предварительная проверка старого формата, SQLite backup в `backups/`,
одна транзакция `BEGIN IMMEDIATE`, замена таблиц и `foreign_key_check`. Card UUID/content,
parent/order сохраняются; прежние Map/Table UUID и payload неизменны. Их корневой
порядок детерминирован: после корневых Cards — Maps в прежнем rowid order, затем Tables.
Assets не изменяются. Отказ/убийство процесса откатывает DDL и payload; backup остаётся.
Неподдерживаемый kind/version или несогласованный inventory диагностируются до записи.
Старое приложение отказывает схеме 5; возврат — через копию старой БД и неизменённые assets.

ApplicationSession хранит current_entity_id; current_card — только совместимая проекция.
Tree получает общий список summaries, поддерживает все виды DnD и root drop. Context
создаёт дочерний документ любого kind. Подтверждение удаления показывает число и виды
документов; закрываются окна удалённых ID. Ссылки из оставшихся карт не каскадируются.
Inspector редактирует общий title/parent; поиск охватывает заголовки документов и доступный
текст payload. WindowManager сохраняет прежние keys Cards/Maps/Tables; новые кубики имеют
`dice:UUID` и сохраняют базовое выражение уже в A. Расчёт и результаты броска не dirty world.

UI state 2 читает version 1: UUID keys и Card expansion восстанавливаются, виртуальные
section keys игнорируются. Старый singleton `dice` не создаёт данные из UI state: такой ключ
пропускается, остальные документы открываются; несовместимый ADS blob не применяется,
используются стандартные вкладки. Именованные кубики создаются явной командой пользователя.

Доказательства: fixture реального schema 4 создан адаптером опубликованного 1835e3b;
проверены миграции 1–4, UUID/content/pins/tokens/grid/строки, перенос/backup/restore,
откат после замены таблиц, убийство отдельного процесса в незавершённой миграции,
integrity_check/FK, mixed DnD и цикл, selection/layout, независимые редакторы и удаление
смешанного поддерева. Команды и фактические результаты — в отчёте итерации 3.

Ограничения: SQL payload loading/FTS остаются прежними; нет универсальных RPG сущностей,
ссылок на другие kinds в публичном URI и внешнего SDK. Настройки/пресеты Dice развиваются
в F; Markdown — до отдельного решения B. Пересмотр при новом module kind или измеренной
необходимости ленивой загрузки; Windows focus/DPI и финальная поставка проверяются в G.
