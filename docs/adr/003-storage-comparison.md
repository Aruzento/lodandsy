# ADR-003: каноническое хранение проекта

Статус: S3 принят владельцем 18.11.2026 вместо S1. ARU-40; задачи ARU-41–54 пересогласованы под SQLite. Реализация начата после решения, её готовность подтверждается отдельно тестами и приёмкой.

Контекст: исходное описание и MVP предпочитают JSON на сущность + производный SQLite
индекс (S1), но оставляют финальный формат открытым. Внешнее редактирование Markdown
не является требованием. Нужно согласованно сохранять и удалять поддерево, позднее
карты, маркеры и таблицы. Нельзя считать replace одного файла транзакцией проекта.

Варианты и выполненный эксперимент:

| Вариант | Прерывание процесса после первой записи удаления A→B | Повторное открытие |
| --- | --- | --- |
| Наивный S1, atomic replace отдельных файлов | A удалена, B ссылается на отсутствующую A | Неконсистентный мир; вариант неприемлем |
| S1 с предварительным журналом удаления | То же промежуточное состояние | Идемпотентный replay удаляет B, C остаётся; индекс перестроен из JSON |
| S3, каноническая SQLite и транзакция | Процесс завершён до commit | Полный rollback: A/B/C идентичны исходным; завершённая транзакция оставляет C |

Дополнительно S3: integrity_check=ok, foreign_key_check пустой, SQLite backup API
создаёт БД с подтверждённым состоянием C. SQLite runtime 3.50.4 из Python 3.14.8.
В S1 проверено восстановление журнала удаления и rebuild производного индекса.
Временные файлы создаются только в локальном temp, данные проекта не затрагиваются.

```powershell
.\.venv\Scripts\python.exe -m prototypes.storage_compare
```

Результаты подтверждают осуществимость обоих вариантов при разных затратах:
S1 проще осматривать и экспортировать по файлам, но нужны журнал/commit/replay для
каждой многообъектной операции, обнаружение частичных изменений, версия и миграции
каждого payload. JSON replace остаётся локальной гарантией. S3 даёт транзакцию данных
проекта, единый номер ревизии и миграции; экспорт JSON/Markdown нужно реализовать явно.
При обоих вариантах assets требуют собственного порядка записи и согласованных backup;
SQLite сама не делает внешние изображения транзакционными.

Предложение владельцу: S3 как единственный канонический контейнер SQLite + assets,
с явным экспортом в JSON/Markdown, если он потребуется. Это отличается от предпочтения
S1 в MVP: причина — подтверждённый rollback многообъектной операции и меньшая собственная
recovery-инфраструктура при отсутствии требования внешнего редактирования. Если для
продукта важнее пользовательские файлы по сущностям, выбрать S1 и принять стоимость
журнала и его отказоустойчивых проверок. Два источника истины не вводятся.

Ограничения: эксперимент использует условные ID и тестовые payload, это не проект
публичной схемы. Он имитирует завершение процесса через os._exit, не power-loss и не
сбой носителя. Не проверены backup assets, повреждение БД/файла, миграции, read-only
будущей версии, блокировка второго писателя, отказ по правам/месту, производительность
сохранения больших миров. До согласования ADR они не заявляются реализованными.
Условие пересмотра: требование внешнего редактирования либо проблемы переносимости,
восстановления или измеренной производительности выбранного store.


Утверждённый контракт владельца: одна каноническая SQLite на проект, sqlite3 без ORM,
Markdown source и стабильные UUID; составные операции транзакционны; foreign_keys
на каждом соединении, иерархия/циклы/порядок валидируются. Разорванные ссылки маркеров
допустимы и не уничтожают маркер. Assets отдельно, пути относительные, публикация
ссылок согласована с файлами при прерывании. Требуются версия схемы, безопасные
миграции, backup/restore, единый autosave/Ctrl+S. Domain/UI не знают SQL. Будущий экспорт
предусмотреть, но не реализовывать в MVP. S1 не поддерживается.

Первичные технические источники:
[SQLite atomic commit](https://www.sqlite.org/atomiccommit.html),
[SQLite backup API](https://www.sqlite.org/backup.html).
